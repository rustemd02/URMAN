## Что такое УРМАН

**УРМАН** — камерная этно-хоррор / мистическая детективная игра о возвращении к корням, памяти, языке и цене правды.

- Сеттинг: татарская деревня Кара-Урман в Татарстане.
- Главный герой: Айдар, городской парень 19–20 лет из Казани.
- Завязка: Айдар после долгого отсутствия возвращается в деревню к бабаю и әби и начинает разбираться, что случилось с его другом детства Маратом.
- Большой слой лора: Кара-Урман веками скрыто сосуществует с существами татарского фольклора: Шурале, Су Анасы, Бичура, Албасты, Убыр и другими.
- Главные темы: память, корни, татарский язык, долг, молчание, взросление, наследование ответственности, цена правды.
- Главная интрига: Айдар думает, что вскрывает человеческий заговор, но постепенно входит в старую систему пакта между деревней и лесом.

УРМАН не должен превращаться в generic horror про монстров. Мифологические существа здесь не «мобы», а часть старого порядка, с которым люди научились жить, торговаться, ошибаться и расплачиваться.

## Как работать с каноном

- Не менять ключевой лор без явной причины и фиксации решения.
- Если появляется противоречие, записывать его в `open_questions.md` или `decision_log.md`.
- Если деталь не подтверждена, помечать её как `Hypothesis` или `Proposal`, а не как факт.
- Не превращать игру в generic horror; сохранять татарский культурный код.
- Не делать мифологических существ простыми монстрами.
- Не делать ислам карикатурным, враждебным или «антифольклорным» слоем. Тимур хәзрәт — моральная и культурная опора, а не декоративный NPC.
- Не делать Айдара «избранным магом». Он наследник линии ответственности, но не супергерой.
- Не решать противоречия молча. Если есть неразрешённые противоречия вроде Айдар/Айрат, Гөлсинә/Миннигуль или двух Маратов — фиксировать их. «Кырлай» в старых материалах считать историческим именем деревни Кара-Урман.

## Mindmap как рабочий инструмент

`docs/urman_knowledge_base/mindmap.md` — центральная карта проекта. Её нужно обновлять, когда:

- появляется новая MVP-критичная система;
- меняется персонаж, сюжетная линия или роль локации;
- добавляется новая ветка ассетов;
- появляется риск или открытый вопрос;
- принимается решение, влияющее на канон или производство.

Использовать теги:

- `[MVP]` — критично для вертикального среза;
- `[RISK]` — риск расползания, противоречия или производственной сложности;
- `[OPEN]` — вопрос не решён;
- `[ASSET]` — требует ассетов;
- `[LANG]` — связано с татарским языком;
- `[TECH]` — требует технической реализации;
- `[NARRATIVE]` — сюжетно важно.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

When the user types `/graphify`, invoke the `skill` tool with `skill: "graphify"` before doing anything else.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- Dirty graphify-out/ files are expected after hooks or incremental updates; dirty graph files are not a reason to skip graphify. Only skip graphify if the task is about stale or incorrect graph output, or the user explicitly says not to use it.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).

## Маршрутизация игровых запусков — поручение настройки стенда 2026-10-05

Перед запуском определить цель: автоматическая проверка или явная просьба
пользователя поиграть/посмотреть игру. Разработка остаётся в текущем checkout.
Автоматические игровые проверки, visual captures и benchmarks направлять на
Windows через `eng/remote-check.py`; настройка и подключения — единый актуальный
`docs/production/WINDOWS_TEST_STATION_RU.md`; краткий старт —
`docs/production/README_WINDOWS_WORKER_FOR_AGENTS.md`. Benchmark использует подходящую
существующую тестовую сцену через режим smoke, без нового тестового набора.

При недоступности станции сообщить конкретную причину, оставить игровую проверку
not-run и продолжить независимую работу. Локальный игровой запуск не является
автоматическим fallback; он допустим только по явному разрешению на конкретный
запуск. Явная просьба «запусти поиграть» выполняется локально на текущем компьютере
пользователя существующими launcher'ами и с прежней защитой данных. Глобального
запрета Mac-Godot нет. При неоднозначном намерении не захватывать управление Mac.

Статические проверки и узкая компиляция без движка могут выполняться локально.
Не тестировать после каждой правки по привычке: выбирать минимальную необходимую
проверку. Удалённый результат относится только к снимку/коммиту, подтверждённому
receipt. Секреты хранятся вне Git и инструкций. Отдельный действующий запрет
игровых проверок в конкретной задаче сохраняется; маршрутизация не даёт нового
разрешения запускать движок. Приёмка настройки стенда разрешает только необходимую
ограниченную Windows-проверку и захват, не возобновляет остальные аудиты.
