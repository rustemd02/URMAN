## UI

### U1 — Решение автора по общей визуальной системе

**Очередь:** `ACT1-UI.1` и `ACT1-UI.7`; правка старой формулировки Persona в `decision_log.md`/UI style guide потребуется
после ответа автора. **Видимый результат:** выбранная автором сквозная система, возвращающая простоту и собственную
идентичность УРМАНА; старый жёлто-чёрный ритм — обязательный вариант сравнения, не команда копировать старые пиксели.
**Пилот:** 2–3 компактных варианта одной и той же тройки экранов — главное меню, диалог с двумя ответами, страница
журнала. Вариант A: строгий жёлто-чёрный с редким акцентом; B: та же читаемость с бумажным/зимним слоем; C только если
первые два не отвечают запросу. Сравнивать в одинаковом размере, шрифте, языке и состоянии фокуса, включая татарские
глифы. **Файлы:** `UrmanUiTheme.cs`, `docs/urman_knowledge_base/ui_style_guide.md`, фактические окна только после выбора.
**Предпосылка:** получить ответ автора «A/B/правки», записать decision; ранние независимые баги делать параллельно.
**Приёмка:** выбранный макет читабелен за секунды, узнаваем, не выглядит клоном Persona, обычный/высокий контраст и
крупный текст работают. **Стоп:** не переписывать все экраны и не менять тему ради одного красивого скриншота до выбора.

### U2 — Одна тема на всех поверхностях без потери функций

**Очередь:** `ACT1-UI.2–.7`, `ACT1-UI.6` уже помечен `completed` функционально; сохранение его функций обязательно.
**Видимый результат:** главное меню/новая игра/продолжить, пауза, настройки и ремап, HUD/прицел/подсказки,
диалоги/субтитры, журнал/книжка/словарь, документы, инвентарь/перенос, old PC и его окна, торговля, банный выбор,
загрузка/ошибка/пустое состояние говорят одним визуальным языком, но ПК сохраняет предметный характер старой ОС.
**Файлы:** `UrmanUiTheme.cs`, `MainMenuUi.cs`, `PauseMenuUi.cs`, `SettingsUi.cs`, `DialogueUi.cs`, `JournalUi*.cs`,
`DocumentUi.cs`, `OldPcUi*.cs`, `ShopUi.cs`, соседние действующие UI owners. **Пилот:** три экрана U1, затем расширение по
фактическому списку UI states, не одноразовые stylebox в каждом файле. **Приёмка:** все действующие функции доступны, нет
пропавших кнопок/статусов, татарские буквы и длинные реплики не обрезаются, статусы «прочитано/закрыто/ошибка/нет
результатов» различимы, клавиатура и геймпад не хуже мыши. **Стоп:** если экран использует свой смысловой контекст (ПК),
адаптировать токены, не натягивать одинаковую красочную панель на всё; не переоткрывать логику словаря/журнала из ТЗ 02.

### U3 — Иллюстрация и настоящая загрузка

**Очередь:** `ACT1-UI.2/.7` + `ACT1-TEXTURE.08`; отдельная карточка `ACT1-UI.LOADING`. **Видимый
результат:** стартовый и переходный экран загрузки с выбранной автором иллюстрацией ImageGen, несколькими вариантами
композиции/состояния и индикатором реального хода операции. **Пилот:** один запуск новой игры и один действительный
переход/восстановление save. Показать `starting`, фактическую загрузку, готовность, честную ошибку/повтор; не симулировать
проценты таймером и не держать экран для «атмосферы». Если операция мгновенна, допустим короткий непрерывный переход без
ложного loader; если долгая, экран не оставляет игрока в пустоте. **Файлы:** существующий UI entry/loading owner,
`game/assets/textures/ui/README.md`/asset registry и версия рисунка, точный prompt/source/SHA/license. **Предпосылка:**
проверить, что реально асинхронно/долго и кто владеет переходом; варианты визуала выбирает автор вместе с U1. **Приёмка:**
экран соответствует выбранному стилю и миру; прогресс/состояние не лжёт, ввод не запускает игру дважды, ошибка даёт
понятный путь назад. **Стоп:** нет ImageGen — оформить нужный asset в существующем реестре/текстурном owner и продолжить
state logic; не подменять генерацию случайной картинкой и не заводить отдельную очередь.

### U4 — Один активный ответ в диалоге и сквозной input/focus

**Очередь:** `ACT1-UI.3/.7`, `ACT1-PLAYER` для биндингов; отдельная карточка `ACT1-UI.FOCUS`. **Симптом:** клавиатурный focus
первого ответа и hover второго визуально выделяют оба. **Пилот:** один диалог с двумя вариантами, мышь после
стрелок/геймпада и обратно. Выяснить, рисуют ли `UrmanUiTheme.BindFocusAsHover`, `DialogueUi` или отдельный stylebox два
независимых активных состояния; чинить общую тему/правило только для реально затронутых controls. **Файлы:**
`DialogueUi.cs`, `UrmanUiTheme.cs`, настройки/remap при необходимости. **Приёмка:** в каждый момент один понятный current
choice, Enter/клик активируют именно его; focus при возврате из настроек, паузы, ПК и mouse capture не теряется;
Tab/стрелки/стик читаемы, видимый focus не исчезает у пользователя без мыши. **Проверка/стоп:** ручной короткий
переключаемый сценарий плюс ближайший существующий UI smoke после фикса; не менять глобально hover, пока не просмотрены
другие окна.

## Звук

### S1 — Короткая карта слышимых событий и мест

**Очередь:** `AUDIO-001` (родитель включает внешние голоса и может оставаться blocked), `ACT1-FOOTSTEP`; отдельная карточка
`ACT1-AUDIO.MAP`. **Видимый результат:** для обязательного маршрута и основных помещений есть читаемая таблица
`событие/условие → источник sample и права → spatial/UI bus → слышимый результат → субтитр/неаудиосигнал → владелец →
статус прослушивания`. Пилотный срез: въезд, разговор, стук, дверь, шаги по двум дорогам/сугробу, дом, ФАП, баня, улица,
ночь у леса. Учесть ветер/лес/редкую человеческую жизнь, не забивать речь и важную тишину. **Файлы:** действующий audio
manifest/README и `AmbientAudioDirector.cs`, `UiFoley.cs`, `FootstepAudioController.cs`, точные call sites. **Приёмка:** у
каждого cue есть смысл, источник, допустимая громкость/дистанция и способ отличить от системной награды; нет неучтённых
повсеместных success-звуков. **Стоп:** карта — адресный production handoff, не новый sound framework и не полный каталог
всей будущей серии.

### S2 — Убрать ложный success и исправить звук стука у общего вызова

**Очередь:** `AUDIO-001`, `ACT1-ADDR`, отдельная карточка `ACT1-AUDIO.CUES`. **Симптомы:** случайный системный «успех» без
объяснимого события; `Act1ConnectedWorld.Addresses.cs` сейчас вызывает `UiFoley.PlayWorld(..., "door_creak")` при
`Knock_*`, что соответствует жалобе на открывание вместо стука. **Пилот:** один рядовой закрытый дом, один сюжетный вход,
одно событие истинного успеха. Найти все caller-ы cue и источник success, отделить `knock`, `door_open`, `unlocked`,
`clue_confirmed` по смыслу, не менять имя глобального sample без анализа остальных потребителей. **Приёмка:** закрытый дом
отвечает именно стуком; звуковой ответ/тишина соответствует состоянию, дверь не слышна, если не открылась; success слышен
только там, где игроку действительно выдан результат, с понятным визуальным/текстовым сигналом. **Проверка/стоп:** узкий
event/call-site осмотр и повторяемый аудиозахват/человеческое прослушивание; не объявлять слуховую приёмку по логам.

### S3 — Шаги различимы, но принадлежат одной зимней среде

**Очередь:** `ACT1-FOOTSTEP.1/.2`, `AUDIO-001`. **Видимый/слышимый результат:** главная и второстепенная дорога,
уплотнённый/мягкий снег, сугроб, доски и интерьер различаются по опоре, но не скачут по уровню и не звучат синтетически.
Текущий контроллер уже классифицирует поверхность по реальному floor contact и имеет off-road категории; сначала проверить
актуальное распределение/семплы, а не добавлять вторую систему. **Пилот:** непрерывный проход дорога → край → мягкий снег
→ сугроб → доска → интерьер с записью текущего surface ID и слышимого sample. **Приёмка:** cadence совпадает со
стопой/скоростью, переход мягок, шаг не заикается вне дороги и не меняется из-за стены или переносимой вещи, в сугробе
слышна та поверхность, на которой реально стоит игрок. **Проверка/стоп:** короткая запись на целевой аудиосистеме +
ближайшая существующая проверка после logic change; технический PASS старого footstep smoke не закрывает натуральность
звука.

### S4 — Среда и баня поддерживают тревогу без UI-награды

**Очередь:** `AUDIO-001`, `ACT1-EX07/.08` и ACT1-BATHHOUSE owner; культурный и сюжетный смысл — ТЗ 01/04. **Результат:**
дом и люди дают локальное тепло, улица жива и чуть тревожна, лес слышен иначе, чем двор; баня меняет
пар/потрескивание/дальний звук по фактическому состоянию печи/воды. Существо не объявляется «дружелюбным чёртом»:
появление и звук обсуждаются в каноне/постановке до генерации, без внезапного generic jump-scare. **Пилот:** вход в тихую
баню → одно осмысленное действие с печью/водой → выход; отдельный уличный отрезок до леса. **Приёмка:** звуки позиционны,
не повторяются навязчиво, изменение объясняется действием, до триггера нет спойлера существа; captions/non-audio cues дают
основную информацию без звука. **Проверка/стоп:** один прослушанный игровой фрагмент на актуальной сборке с/без звука; без
нового музыкального пакета до доказанной потребности.

## Взаимодействия и транспорт

### M1 — Решить судьбу ложных интерактивов по игровому результату

**Очередь:** `ACT1-MECH-AUDIT.1–.4`, `ACT1-EX00/.03/.11/.13/.14`. **Результат:** на основном пути нет действия ради кнопки
и записки ради награды; одинаковое понятное правило работает в сходной ситуации. Общая ревизия всех interaction IDs нужна,
но в производство вести короткими зонами: старт/Z13 → ФАП/D13 → бабаев двор/Z18/И22 → баня → остальной путь. Для каждой
строки: ID/локация, что игрок видит до нажатия, действие, физический/сюжетный результат, повторяемость на аналогах,
зависимости, решение `keep/fix/remove`, влияние на save/квест/EX. Оценка автора «90%» — сигнал проблемы, не подтверждённая
доля автоматического удаления. **Пилот:** первые 5–8 интерактивов маршрута; показать автору 2–3 спорных решения.
**Приёмка:** каждый оставленный тип имеет ясное назначение или подготовленный поздний payoff; удалённый объект не
оставляет текстового обещания, пустой кликабельной цели и сломанного save. **Стоп:** прежний контракт «≥3 применения» не
выполнять искусственными копиями; если единственное сюжетное действие действительно работает, предъявить его как
обоснованное исключение владельцу очереди.

### M2 — Первые конкретные предметы: Z13, ФАП, колодец и мостик

**Очередь:** `ACT1-MECH-AUDIT.2/.3/.4`, `ACT1-EX03/.05/.11`. **Z13:** вращающаяся «Фаб Юл» сейчас просто переворачивается.
Выбрать: убрать interactable, дать понятный физический эффект/ограничение, либо оставить как ранний наблюдаемый намёк с
поздним payoff; предложение автора «крутить свободно» — вариант, не требование бесконечной анимации. **ФАП:** кружка у
входа и D13-предметы должны показывать, зачем их можно трогать, либо перестать быть интерактивными; вход/сопоставление
фактов принадлежит ТЗ 02. **Колодец/сарай:** варежка и щеколда не должны автоматически выдавать очередную необязательную
записку; бытовая функция вещи может остаться. **Z18/И22:** развернуть/убрать лавку с нелепым держателем, мостик/смахивание
снега связать с настоящим проходом/повторяемым правилом или снять ложную цель; географическое перемещение — ТЗ 03.
**Пилот:** один выбранный предмет каждого класса, затем поиск аналогичных consumer-ов. **Приёмка:** игрок может
предсказать эффект по форме/состоянию, видеть результат и применить правило в другом логичном месте; квестовые флаги и EX
не исчезают молча. **Проверка/стоп:** короткий игровой проход до/после на отдельном save, без нового универсального
«конструктора головоломок».

### M3 — Тепло/вода бани как понятная цепочка

**Очередь:** `ACT1-EX07`, ACT1-BATHHOUSE, `ACT1-MECH-AUDIT.3`, `AUDIO-001`; пространственная постановка I5 ТЗ 04.
**Результат:** долить воду или затопить печь имеет видимую и слышимую причину/следствие, доступное состояние и
ограничение; игрок понимает, что изменилось, не получает тайную награду за бессмысленную рутину. **Пилот:** один обычный
путь дрова/печь → тепло → вода/пар, с одним вариантом отказа/возврата; проверить текущие `Act1ConnectedWorld.Bathhouse.cs`
и `RuntimeBridge.Bathhouse.cs` прежде чем менять семантику. Существо появляется только по утверждённому условию и не как
приятный NPC с первого взгляда. **Приёмка:** состояние сохраняется согласно действующему контракту, повтор не плодит
одинаковые эффекты, результат связан с местом/расследованием, а не с числом нажатий. **Проверка/стоп:** один нормальный и
один прерванный локальный сценарий; канонический статус обитателя и момент раскрытия остаются вопросом автора/нарратива,
не выводом из этого ТЗ.

### M4 — Поездка между домами без произвольной дорожной клетки

**Очередь:** `ACT1-TRANSPORT`, `ACT1-EX00`, `ACT1-VILLAGE-LAYOUT`; отдельная карточка `ACT1-TRANSPORT.ROUTE`. **Результат:** текущая
Нива и другие реально доступные средства могут проехать по правдоподобной свободной поверхности деревни, включая
допустимый двор/снег, и остановятся из-за видимого уклона, глубины, забора, воды, пешехода или узкого прохода, а не по
условной границе «главная дорога кончилась». `VehicleFleet.EvaluateTravel` уже проверяет границы terrain и зовёт
`_world.CanVehicleTraverse`; сначала выяснить, какой отказ был в авторской точке и не является ли он геометрией/коллизией.
Лесные сюжетные переходы остаются явными и безопасными. **Пилот:** главная дорога → соседний двор → неглубокий снег →
разворот/выезд; зафиксировать вердикты и путь игрока пешком как сравнение. Не добавлять мотороллер, если Нива/мотоцикл уже
дают полезное перемещение после расширения деревни. **Приёмка:** транспорт экономит осмысленный путь между домами,
сообщение отказа отражает видимую причину, машина не телепортируется/не застревает/не проезжает сквозь границу Акта II,
посадка/выход и сохранение устойчивы. **Проверка/стоп:** один контролируемый заезд и возврат плюс существующий узкий
vehicle check после логики; не отключать весь road graph в надежде «разрешить всё».

### M5 — Салон Нивы и пассажирский ракурс

**Очередь:** `ACT1-TRANSPORT`, `ACT1-TEXTURE.07`, ASSET/vehicle owner; отдельная карточка `ACT1-TRANSPORT.CABIN`. **Результат:**
педали двигаются по реальному газу/рабочему тормозу, ручник соответствует уже существующему `ParkingBrake`, зеркальная
подвеска не бьётся о салон, спинки и боковые/задние стыки окна цельны. Удачный руль сохранить. Если в прологе принят
подвоз Айдара бабаем, пассажир видит деревню с заднего сиденья без выдачи управления; это **отдельная зависимость** от ТЗ
01, а не автоматический новый режим вождения. **Файлы:** `VehicleController.cs`, `VehicleVisualFactory*.cs`, Blender
vehicle source/registry; формы/материалы — ТЗ 05. **Пилот:** первая посадка и один короткий круг с разгоном, торможением,
остановкой и взглядом назад/влево; пассажирский шот только после storyboard. **Приёмка:** положение рычагов/педалей
совпадает с состоянием, charm затухает после манёвра, не пересекает зеркало/крышу, спинки не кривятся в POV, стекло
примыкает к кузову без дыр; повторный вход и save/load не сбивают салон. **Проверка/стоп:** короткое POV-видео и вид
снаружи; не симулировать сложную механику сцепления/подвески ради видимой педали.

### M6 — Снег, след и перенесённая вещь имеют общую физическую опору

**Очередь:** `ACT1-EX01/.05`, `ACT1-PLAYER`, ACT1-DEPTH; W10 ТЗ 03 владеет размещением/мешем снега. **Результат:** текущий
удачный след остаётся, появляется на проходимом сугробе по высоте шага и не рисуется на воде/в воздухе; поставленная
палка/предмет имеет видимый согласованный collider и не блокирует проход только с одной стороны. `SnowTrampleField` сейчас
session-only presentation, не меняет physics или save: не обещать деформируемый коллайдер и persistence без отдельного
решения. **Пилот:** ровный снег → один сугроб → перенос и постановка палки рядом с узким проходом → обход с двух
направлений/повторное поднятие. **Приёмка:** визуальный след и `footstepSurface` соответствуют реальной опоре, снег не
просвечивает в предмет, коллизия переносимой вещи совпадает с формой/состоянием, игрок может убрать собственное
препятствие, нет одностороннего невидимого блока. **Проверка/стоп:** боковое видео контакта и короткий обратный проход;
геометрические сугробы О9/Р13–Р15 исправляет W10, не этот runtime пункт.

## Производительность

### P1 — Воспроизвести жалобу на M1 как измерение целевой машины

**Очередь:** `FINISH-07`, ACT1-TECH/перформанс owner; отдельная карточка `ACT1-PERF.PROFILE`. **Симптом:** автор сообщает менее
35–40 FPS на Mac с M1 при любых настройках; текущие M4 Pro около 120 FPS, авто-переход в safe mode и старые headless PASS
не опровергают жалобу. **Пилот:** на том M1 или сопоставимом целевом M1 записать exact build/source commit, способ запуска
(пакет/обёртка/редактор), macOS/GPU, питание/термальное состояние, разрешение/Retina scale, renderer, пресет, MSAA, scale,
время прогрева; тот же короткий маршрут у старта, улицы, леса и ФАПа на medium/low. Использовать уже имеющиеся
`--print-fps --no-auto-performance-fallback`, `--urman-perf-probe`, `eng/benchmark-act1-demo-package.sh` и guard, не новый
профайлер. Разделить CPU/GPU/frame time, p95/max, первые кадры и sustained нагрузку; сравнить заметное изменение настроек
с фактическими настройками viewport, а не с надписью в меню. **Приёмка:** найден конкретный bottleneck или точно
ограниченный внешний/launch blocker с логами и воспроизводимым маршрутом; нет утверждения «исправлено» по
M4/автоматическому safe profile. **Стоп:** без M1/его логов пункт остаётся target-host external/not-run; не переписывать
рендер или урезать лес вслепую.

### P2 — Узкая правка подтверждённого узкого места

**Очередь:** `FINISH-07` и фактический owner найденного в P1 участка. **Результат:** после адресной правки тот же M1, тот
же маршрут и viewport достигают согласованной нижней границы **35–40 FPS** без сломанной читаемости, либо
документированная внешняя причина/ограничение остаётся открытой. Приоритет: регресс независимо от пресета → проверить
CPU/импорт/драйвер; разница High/Low → конкретный GPU/материал/LOD; короткий hitch → отдельный spike, не среднее.
**Предпосылка:** P1, фиксированный кандидат и сверка кадра до/после. **Приёмка:** p95/frame pacing и минимум на неприятных
участках лучше, настройки действительно дают измеряемую разницу, качество ключевых сцен/густота леса не уничтожены.
**Проверка/стоп:** повторить только тот же target-host маршрут и ближайший performance gate после правки; если бюджет
35–40 невозможен на указанном оборудовании без продуктовой потери, предъявить автору измеренный tradeoff, а не объявлять
PASS по более сильному Mac.

## Граница завершения

Документ не требует новых общих UI/audio/mechanics frameworks. Владелец реализации берёт только затронутые существующие
файлы и соединяет результат с текущим backlog ID. Точные права аудио/изображений, доступность субтитров, ремап ввода и
сохранение игроковых настроек обязательны. Для обычного игрового пути нужен короткий человеческий просмотр/прослушивание,
иначе соответствующие художественный/звуковой критерии остаются `external/not-run`. Удаление механики, новая концовка,
новая логика сейвов, новая катсцена и публикация из этого ТЗ не следуют.
