# URMAN Studio — техническое задание на визуальный редактор игры

Версия: 1.0, 27 сентября 2026. Статус: проект ТЗ для рассмотрения автором.

Основание: интервью с автором в отдельной беседе 26–27 сентября 2026. Подтверждённые продуктовые требования отделены ниже от предлагаемых технических решений. Документ не утверждает готовность функций и не разрешает автоматически начинать реализацию, менять канон, публиковать игру или отправлять изменения в Git.

Это спецификация системы, а не новая очередь задач. После согласования реализация должна планироваться в действующем `docs/urman_knowledge_base/execution_backlog.json`. Текущая работа над игрой этим документом не изменяется.

## 1. Назначение и результат

Создать отдельное приложение для macOS, в котором автор без опыта работы с игровыми редакторами может визуально изменять существующий URMAN и создавать новый игровой контент без программирования, ручного JSON, командной строки и знания устройства Godot.

Основной рабочий цикл: открыть деревню → разместить или изменить объекты → связать персонажей, предметы, диалоги и события в квест → настроить последствия для мира → пройти получившийся эпизод → сохранить и передать изменения другим участникам.

Главный сценарий приёмки: после встроенного знакомства с интерфейсом автор за один вечер самостоятельно перестраивает участок улицы, добавляет персонажа с побочным квестом, настраивает два исхода с разными последствиями для мира и проходит оба. Рабочее определение «вечера» для проверки — до четырёх часов активной работы; это предлагаемая цель удобства, не обещание срока разработки.

Редактор должен работать с настоящими игровыми данными и тем же runtime, который исполняет URMAN. Демонстрационный конструктор, результат которого разработчик затем вручную переносит в игру, не соответствует ТЗ.

## 2. Подтверждённые требования и границы

| ID | Требование автора |

| U02 | Интерфейс рассчитан на человека без опыта; обучение действиями, понятные названия. |
| U03 | Деревня и квесты одинаково важны; первая полезная поставка соединяет оба направления. |
| U04 | Свободный 3D-вид и вид сверху. Каталог готовых моделей по категориям, по принципу режима строительства The Sims. |
| U05 | Дом с интерьером и внешним видом — единый редактируемый объект. Обязательного конструктора домов из стен и этажей нет. |

| U08 | Анимации выбираются из подготовленного каталога. Последний ответ уточняет прежнее пожелание создавать скелетные анимации: ручной редактор ключей костей не является обязательным. |
| U09 | Основные и побочные квесты, последовательность, параллельность, зависимости, развилки, провалы, повторения, сроки и отложенные последствия. |
| U10 | Внутри квеста — синхронизированные список шагов и граф. Сортировка списка и изменение порядка прохождения — разные действия. |
| U11 | Триггеры и квестовые персонажи располагаются на карте; выполнение квеста может менять её устройство. |
| U12 | Диалоги с условиями и выбором; постановка сцен списком действий и монтажной шкалой. |
| U13 | У NPC маршруты, расписания, занятия, реакции, отношения, сопровождение и уход от опасности. Общая память о поступках и универсальный обмен предметами с NPC не нужны. |
| U14 | Полное редактирование предметов и остальных перечисленных игровых систем, включая журнал, улики, язык, старый ПК, магазины, транспорт, головоломки и UI. |
| U15 | Запуск выбранного состояния, диагностика условий, пауза и пошаговая проверка. |
| U16 | Встроенный ИИ не нужен. Нужны устойчивые копируемые ID и передача разработчику точного контекста, в том числе нового черновика и конкретного сбоя. |
| U17 | Отмена, повтор, автосохранение, восстановление после сбоя, именованные версии. Альтернативные авторские варианты мира не нужны. |
| U18 | Возможна одновременная работа нескольких людей; изменения должны объединяться, а конфликты — решаться через понятный интерфейс. |

Разъяснения границ:

- Сюжетные состояния одной карты входят в продукт. Отдельная система авторских веток «деревня A / деревня B» не входит.
- Точная квестовая проверка «выбран ответ X» входит. Универсальная симуляция памяти NPC обо всех поступках игрока не входит.
- Передача квестового предмета и явно оформленный магазин входят. Произвольный бартер с каждым NPC не входит. Это трактовка совместных ответов U13/U14 для проверки автором.
- Редактирование моделей входит; специализированный профессиональный пакет уровня всего Blender не является критерием. Обязательные операции перечислены в §7, и их нельзя заменить одной кнопкой импорта.
- «Без кода» относится ко всем перечисленным сценариям. Новая физическая механика вне каталога действий требует разработки нового исполняемого действия; редактор не обещает конструировать любые алгоритмы мира из произвольного кода.
- Платформа редактора — macOS. Это не меняет платформы поставки самой игры.
- Интерес исследования — художественный результат, проверяемый человеком. Длина маршрута, число объектов и технические проверки его не доказывают.

## 4. Рабочее место и интерфейс

### 4.1. Организация экрана

Предлагаемый интерфейс: спокойная тёмная тема, контрастный текст, крупные превью, умеренные цветовые акценты, минимум постоянных панелей. Вид игры остаётся главным содержимым. Это направление для прототипа, а не уже принятый визуальный дизайн.

| Область | Содержимое |
|---|---|
| Верхняя строка | Проект, сохранение, отмена/повтор, общий поиск, «Проверить», «Играть отсюда», состояние совместной работы. |
| Левая навигация | Мир, Квесты, Диалоги и сцены, Персонажи, Предметы, Контент, Интерфейс игры. Внутри раздела — список и фильтры. |
| Центр | 3D/план деревни, граф, список шагов, диалог или рабочий холст выбранного раздела. |
| Правая панель | Человеческое имя, свойства, связи, ID, кнопки «На карте», «Где используется», «Скопировать контекст». |
| Нижняя выдвижная панель | Каталог объектов, монтажная шкала или диагностика по выбранной задаче. |

Обязательные требования:

- UX01. Каждый раздел открывается в постоянной вкладке. Переход по связи сохраняет положение камеры, масштаб графа, выделение и незаконченный ввод в исходной вкладке; доступна кнопка «Назад».
- UX02. Список квестов не исчезает при выборе объекта на карте; допустим разделённый вид «карта + квест». Панель свойств можно закрепить.
- UX03. Никаких автоматических закрытий формы во время ответа, ввода или просмотра. Ошибка валидации сохраняет введённое; фоновые обновления не крадут фокус.
- UX04. Действия доступны кнопками и контекстным меню, сочетания клавиш — ускорение. Поддержать мышь и трекпад без обязательной средней кнопки.
- UX05. Cmd+Z / Cmd+Shift+Z, Cmd+S, копирование/вставка, дублирование, поиск; команды действуют в понятном контексте, горячие клавиши не перехватывают ввод текста.
- UX06. Размер интерфейса 100–150%, читаемые подписи, клавиатурная навигация, видимый фокус. Статусы различаются текстом/значком, а не только цветом. Русский интерфейс, корректные татарские символы.
- UX07. Основные поля показаны сразу; технические параметры — в «Дополнительно». ID копируется в один клик, но не заменяет имя.
- UX08. Общий поиск находит по имени, ID, типу и тексту реплики; можно вставить ID или ссылку из сообщения разработчика.
- UX09. Пустые экраны объясняют первый шаг. Первое знакомство — короткий встроенный маршрут «поставить объект → отменить → привязать событие → попробовать» с возможностью пропустить и повторить.
- UX10. У удаления виден список затрагиваемых связей. Массовое удаление/замена требует просмотра результата; обычное перемещение не прерывается подтверждениями.
- UX11. Состояния «Сохранено», «Есть изменения», «Черновик не готов к запуску», «Конфликт», «Запущена проверка» разделены. Сохранить незаконченный квест можно всегда, если запись на диск доступна.

### 4.2. Что согласовать визуально до основной реализации

Подготовить связанный кликабельный прототип пяти экранов: мир с каталогом; карта с выбранным триггером и квестом; список/граф квестов; монтажная шкала; разбор конфликта. Прототип должен включать пустое состояние, ошибку и незаконченный черновик. Автор проверяет понятность, плотность и размер элементов; статичная красивая картинка недостаточна.

## 5. Идентичность данных и единые связи

- DATA01. Сущность получает неизменяемый ID в момент создания, до первого ручного сохранения. Это относится к квесту, его шагу, цели, ребру/переходу, условию, действию, реплике, объекту мира, триггеру, точке пути, шоту и экземпляру предмета.
- DATA02. Существующие ID сохраняются. Новые ID создаются автоматически с namespace и случайным уникальным компонентом; названия можно менять без разрыва связей. Пользователь не обязан придумывать уникальный текстовый ключ.
- DATA03. Определение предмета/персонажа/модели и размещённый экземпляр имеют разные ID. Повторный запуск квеста имеет отдельный run ID; конкретное срабатывание — occurrence ID.
- DATA04. Дублирование создаёт новые ID; внутренние ссылки копируемой группы переназначаются на её копии, внешние остаются внешними. Перед применением показана сводка.
- DATA05. У всего контента есть имя, тип, теги, ревизия, состояние готовности, автор/последнее изменение и список использований. Документ/ресурс открывается по ID после переименования и перемещения файла.
- DATA06. Один общий механизм ссылок связывает карту, квест, диалог, предмет, сцену и UI. Отдельные несогласованные списки «связанных объектов» по подсистемам запрещены.
- DATA07. Граф и список — представления одной логики. Координаты блоков и личная раскладка панелей не влияют на прохождение и не загрязняют общие данные игровыми изменениями.
- DATA08. Автоматическое изменение существующих ручных данных генератором/импортом предваряется сравнением. Новый импорт не меняет ID и не восстанавливает удалённые автором объекты без явного решения.

## 6. Мир и каталог объектов

### 6.1. Каталог

- WORLD01. Категории: дома и постройки; заборы/ворота; дороги и покрытия; деревья/кустарники; камни/снег; мебель; бытовой реквизит; инструменты; источники света; персонажи; транспорт; игровые предметы; звук и эффекты; служебные точки/триггеры.
- WORLD02. Карточка содержит превью, название, размеры в метрах, материалы, состояние коллизии, совместимость с взаимодействиями, источник/лицензию и ID. Поиск, фильтры, избранное и недавно использованные.
- WORLD03. Перетаскивание из каталога показывает полупрозрачное размещение и допустимость позиции; щелчок подтверждает, Escape отменяет. Статичный и физический объект различаются явно.
- WORLD04. Начальный каталог включает все доступные подходящие ассеты URMAN, а не пустые категории. Для основного сценария в нём должны быть работоспособные дом с интерьером, калитка, забор, растительность, реквизит, подбираемый предмет, NPC и источник света.
- WORLD05. Импорт модели, материала, текстуры, звука или анимации выполняется через окно/drag-and-drop. Первый обязательный формат моделей — glTF/GLB; изображения — PNG/JPEG; звук — WAV/OGG. Другие форматы добавляются только с проверенным импортёром.
- WORLD06. Проверяются масштаб, оси, материалы, ссылки на текстуры, скелет и коллизии; нет молчаливого успеха с отсутствующей частью ресурса. Повторный импорт показывает, что изменится во всех экземплярах.

### 6.2. Расстановка и окружение

- WORLD07. Перемещение, вращение, масштаб по осям; числовой ввод; локальные/мировые координаты; сетка; привязка к поверхности; выравнивание; группировка; множественное выделение; дублирование; блокировка от случайного выбора.
- WORLD08. Вид сверху с измерениями, орбита, свободный полёт, фокус на выделенном, переход на уровень глаз. Слои видимости: архитектура, растительность, NPC, предметы, триггеры, маршруты, камеры, звук, коллизии.
- WORLD09. Дом перемещается вместе с интерьером, дверями, связанными входами и дочерними точками. Полупрозрачные стены/скрытие крыши позволяют редактировать комнаты без разборки дома. Для технически отдельной интерьерной сцены сохраняются связь и переход, без требования одномоментно переделать загрузку всех интерьеров.
- WORLD10. Рельеф: поднять/опустить, сгладить, выровнять по высоте, нарисовать покрытие; виден размер и сила кисти. Дороги и тропинки — редактируемые линии с шириной, материалом и точками соединения.
- WORLD11. Кисть растительности: выбранный набор моделей, плотность, диапазон масштаба/поворота, исключаемые участки. Результат воспроизводим, штрих отменяется одной командой. Кисть не засыпает защищённый проход без предупреждения.
- WORLD12. Настройка материалов, освещения, времени суток, тумана, снега/осадков, ветра и звуковых зон с предпросмотром. «Посмотреть ночью» не меняет сюжетное время без отдельного действия.
- WORLD13. Показ коллизий, проходов, доступности двери/предмета, маршрута NPC и препятствий. Перестановка объекта обновляет связанные коллизии и навигацию; видимый объект и его невидимый физический двойник не расходятся.
- WORLD14. Масштабирование дома предупреждает о слишком узких проходах и изменении точки взаимодействия. Проверки достижимости относятся к выбранному состоянию мира и профилю персонажа, а не объявляют всю локацию гарантированно проходимой.
- WORLD15. Процедурно созданный участок можно сделать авторским: получить реальные редактируемые экземпляры с ID. После этого генератор не владеет их трансформациями. Повторное применение генерации — отдельная операция с просмотром разницы.

## 7. Встроенное моделирование

Это самостоятельный крупный модуль полной поставки. Каталог и изменение трансформаций его не заменяют.

- MODEL01. Открыть модель из мира/каталога; выбрать изменение общего ресурса с показом использований либо создание отдельного ресурса для выбранного экземпляра. Исходный импортированный файл не затирается.
- MODEL02. Создание примитивов, редактирование вершин/рёбер/граней, выделение связанной части, перемещение/масштаб/поворот, вытягивание, разрез, фаска, объединение/разделение, зеркальная симметрия, исправление нормалей.
- MODEL03. Скульптурные кисти перемещения, объёма, сглаживания и симметрии достаточны для изменения щёк, подбородка, носа и общей формы головы. Поддержать числовые параметры пропорций там, где они предусмотрены моделью; нельзя обещать произвольные ползунки для любого импорта.
- MODEL04. Создание одежды из основы/выделенной поверхности, толщины и посадки; назначение материалов, простая UV-развёртка/проекция и покраска. Просмотр пересечений на обязательных анимациях из каталога.
- MODEL05. Создание нового персонажа начинается с пустой модели либо заготовки, но результат должен быть пригоден для игры: скелетный шаблон URMAN, привязка/коррекция весов, сокеты для предметов и проверка набора движений. Настройка скелета для совместимости входит; сочинение анимаций костей по ключам не требуется U08.
- MODEL06. Геометрия, материалы, коллизия, скелет и производные ресурсы обновляются согласованно. Повреждение совместимости со старой анимацией/LOD явно показано до применения.
- MODEL07. Критерии модуля: создать новый простой предмет; изменить проём готового дома; изменить лицо персонажа; сделать элемент одежды; создать нового персонажа из заготовки/геометрии и проиграть на нём движения. Все пять сценариев выполняются внутри Studio без скрытого ручного запуска Blender.

В реализации допускается повторно использовать существующие библиотеки и поставляемые вспомогательные инструменты за интерфейсом Studio. Лицензия, установка и работа на Mac должны быть проверены; требовать от автора самостоятельно выполнять внешние команды нельзя. Конкретное средство моделирования выбирается отдельным ограниченным техническим исследованием до обещания срока этого модуля.

## 8. Персонажи и каталог анимаций

- NPC01. Карточка персонажа: имя, модель, портрет, роль, доступные диалоги/квесты, исходное место, расписание, маршруты, занятия, отношения и реакции. Персонаж выбирается в каталоге и ставится на карту.
- NPC02. Расписание редактируется блоками времени: место, занятие, путь, условие. Конфликты одновременных занятий видны. Квест может временно занять персонажа, после чего он возвращается к расписанию.
- NPC03. Маршруты рисуются точками в мире; доступны ожидание, взгляд на цель, поворот, сопровождение игрока и уход в безопасную точку. У недостижимого пути показана причина и действие при неуспехе, чтобы квест не зависал бессрочно.
- NPC04. Отношения задаются явными параметрами/условиями; нет фонового накопления общей памяти о каждом поступке. Квестовые факты остаются обычным состоянием истории.
- ANIM01. Каталог с движущимися превью и категориями: ожидание, ходьба/бег, разговор/жесты, эмоции, работа/взаимодействие, сидение, подбор/перенос, реакция на опасность. Пустая категория не считается поставленным набором.
- ANIM02. Выбор клипа на текущем персонаже; скорость, петля, обрезка начала/конца, переход, положение относительно мира, совместимость со скелетом. Предупреждение о несовместимом клипе вместо случайно деформированного персонажа.
- ANIM03. Минимальная поставка движений: Idle, Walk, Run, Talk, поворот, указание рукой, поднятие/перенос/передача предмета, посадка/сидение/вставание, испуг и рабочее действие для квеста. Названия описывают назначение; конкретное число художественных вариаций определяется каталогом поставки.
- ANIM04. Импорт, назначение и предварительный просмотр анимации; повторное использование на совместимых персонажах. Автоматическое переназначение скелета не считается гарантированным для любого стороннего файла.
- ANIM05. Действие «идти к точке» связывает реальное перемещение и клип; явный выбор владельца перемещения предотвращает двойной root motion и скольжение. Предмет крепится к выбранному сокету, контакт и клиппинг проверяются в движении.

## 9. Квесты: кампания, списки, граф и логика

### 9.1. Общая картина

- QUEST01. Представления: основная сюжетная линия по актам/главам; список побочных квестов; все квесты с фильтрами; граф зависимостей; квесты на карте.
- QUEST02. Карточка: название, краткая цель, авторский статус, тип, персонажи, места, условия доступности, предполагаемая длительность, зависимости, награды/исходы, связанные документы и количество проблем. Авторский статус не смешивается со статусом квеста в пробном прохождении.
- QUEST03. На графе различимы: «открывает», «требует», «исключает», «можно параллельно», «меняет общий объект». Тип связи имеет текст; условие можно открыть из стрелки.
- QUEST04. Перестановка карточек меняет организацию списка. Команда «Сделать доступным после…» отдельно меняет реальную зависимость и показывает последствия для других квестов. Положение по горизонтали не исполняется как сюжетная логика.
- QUEST05. Фильтры по месту, персонажу, предмету, главе, готовности, ошибкам и участнику; поиск по тексту/ID; выделение всех предков/последствий выбранного квеста.

### 9.2. Содержание квеста

- QUEST06. Список шагов и граф редактируют одну модель, включая ветви, параллельные цели и соединения. Сложная ветка показывается вложенным блоком/ссылкой; переключение не уплощает и не удаляет структуру.
- QUEST07. Основные элементы: стартовое событие, условие, действие, ожидание события, цель, ветвление, параллельная группа, объединение ветвей, результат и завершение. Для параллельной группы явно выбирается «все», «любая» или «N из M».
- QUEST08. Условия собираются человеческими фразами: «Игрок имеет 3 доски», «Квест завершён», «Улика подтверждена», «Сейчас вечер», «Выбран ответ…». Группы И/ИЛИ/НЕ видны без синтаксиса языка программирования. Типизированные поля исключают выбор предмета вместо персонажа.
- QUEST09. Состояния: недоступен, доступен, активен, завершён, провален, отменён. Повторяемость задаётся явно; новый запуск имеет собственный run ID, набор сбрасываемых целей и политику повторной награды.
- QUEST10. Таймер имеет понятный источник: игровое время или время активной сессии. По умолчанию меню и закрытая игра не расходуют время активной сессии. Другой режим выбирается явно; остаток сохраняется.
- QUEST11. Отказ, провал и альтернативный успех могут вести к разным квестам и состояниям мира. Долгосрочные последствия привязаны к устойчивым фактам/ID, а не к тексту реплики.
- QUEST12. У каждого ожидания определена реакция на исчезновение цели/недоступность NPC/прерванную сцену. Бессрочное ожидание допустимо только как явное авторское решение.
- QUEST13. Создание из шаблона: разговор → поиск → возврат; доставка; исследование улики; открытие пути; сопровождение; выбор с двумя исходами. Шаблон создаёт обычные редактируемые сущности с новыми ID.
- QUEST14. Неполный квест сохраняется как черновик; проблемы появляются рядом с конкретным шагом. Нельзя молча запускать старую версию вместо текущего черновика: запуск либо указывает использованную ревизию, либо объясняет блокирующую ошибку.

## 10. Триггеры на карте и сюжетные изменения мира

- TRIG01. Триггеры: вход/выход/нахождение в области, взаимодействие с объектом, разговор/выбор ответа, подбор/применение/передача предмета, этап квеста, время, окончание действия/анимации, зарегистрированное событие игрового механизма.
- TRIG02. Пространственные формы: коробка, сфера и многоугольная область с высотой; размеры меняются ручками в мире. Фильтр актёра обязателен: например, только игрок, а не любой NPC.
- TRIG03. Выбор триггера показывает связанные квесты, условие, действие и текущую причину несрабатывания. Выбор шага квеста подсвечивает триггер; «Создать область на карте» сразу создаёт связь.
- TRIG04. Частота: один раз на кампанию, один раз на запуск квеста, при каждом новом входе или с указанной задержкой. Повторное получение того же occurrence ID не повторяет награду и изменение мира.
- TRIG05. При связывании с активным квестом явно задано, считать ли уже выполненное условие: игрок уже внутри зоны, предмет уже подобран. Нет неявной необходимости выйти и зайти заново.
- STATE01. Автор задаёт базовое состояние объекта и именованные сюжетные состояния: например, «калитка закрыта», «сломана», «починена». Состояние может менять модель, трансформацию, видимость, коллизию, доступность взаимодействия, звук и маршруты.
- STATE02. Пакет изменений мира объединяет несколько объектов: убрать завал, открыть проход, переместить NPC и включить новую точку интереса. Предпросмотр «до/после» относится к этому пакету, не создаёт альтернативную авторскую карту.
- STATE03. Причина изменения хранится как связь с квестом/событием. Редактор показывает всех владельцев одного свойства; несовместимые одновременные изменения требуют явного приоритета/взаимоисключения. Порядок загрузки файлов не решает конфликт.
- STATE04. Постоянное состояние подтверждается в одной игровой транзакции. Представление, физика и навигация согласованно применяются до следующего игрового взаимодействия; загрузка восстанавливает их из подтверждённого состояния.
- STATE05. Перемещение/появление геометрии поверх игрока или NPC требует авторской политики: отложить до освобождения, показать переход с безопасной точкой либо запретить. Нельзя молча телепортировать игрока или заключать его в коллизию.
- STATE06. Состояние после пропуска сцены совпадает с обычным завершением по постоянным фактам и объектам; скрытые декоративные промежуточные положения не попадают в итоговое сохранение.

## 11. Диалоги

- DLG01. Сценарный список и граф реплик/ответов; говорящий, адресат, текст, эмоциональная/анимационная подача, камера, звук, условия и эффекты.
- DLG02. Несколько участников, условные варианты ответа по предметам/знаниям/решениям/отношениям, проверки заданного параметра, прерывания и необязательный таймер выбора. Недоступный ответ можно скрыть или показать с причиной.
- DLG03. Каждая проверка и ограниченный выбор имеют явный исход неуспеха/таймаута. Нельзя включить случайную проверку без указания параметров и воспроизводимого игрового RNG.
- DLG04. Локализация: русский и татарский контент, существующие другие переводы не теряются; подсветка отсутствующего перевода, татарских учебных токенов и слишком длинной реплики. Текст хранится в существующей системе локализованных данных.
- DLG05. Импорт реплики актёра, прослушивание, громкость, субтитр, транскрипт и длительность. Отсутствующая озвучка помечается явно; временная озвучка не выдаётся за принятую автором.
- DLG06. Быстрое проигрывание диалога с выбранными предметами/знаниями; показ недоступных веток и причин. Назад в редактор возвращает к выбранной реплике.
- DLG07. Показ в реальном игровом UI: перенос строк, выбор, фокус, управление клавиатурой и настройки доступности. Завершение/прерывание диалога освобождает ввод и камеру.

## 12. Катсцены и монтажная шкала

- CINE01. Список действий и временные дорожки одной сцены. Дорожки: персонажи/перемещение, анимации, камеры, реплики/субтитры, звук, предметы/эффекты, события мира.
- CINE02. Добавление клипа перетаскиванием, изменение длительности, паузы, перекрытия, привязка к началу/концу другого события, маркеры. Действия с неизвестной длительностью показываются как ожидания, а не ложные фиксированные секунды.
- CINE03. Камера выставляется из текущего вида; настраиваются цель, положение, FOV, плавность, движение по точкам и границы кадра с учётом субтитров. Можно следить за NPC/сокетом. Ручные значения доступны дополнительно.
- CINE04. Анимации и движения выбираются из каталогов и маршрутов; касание/передача предмета привязываются к маркеру и сокету. Предпросмотр не скрывает проблемы ног, одежды и пересечения объектов.
- CINE05. Перемотка показывает презентационное состояние без выдачи предметов и записи прогресса. Для событий с физикой используется восстановление исходного снимка и воспроизведение до точки; мгновенная обратная симуляция произвольной физики не обещается. Пока идёт пересчёт, виден статус.
- CINE06. Постоянные игровые эффекты отделены от временной постановки. Пропуск применяет предусмотренный итог ровно один раз, а не быстро проигрывает все побочные действия.
- CINE07. Загрузка во время сцены следует выбранной и показанной политике контрольной точки: восстановить поддерживаемую точку либо начать безопасный фрагмент заново. Сохранение содержит ID сцены/контрольной точки; награды не удваиваются.
- CINE08. Обычное завершение, пропуск, отмена пробного запуска и ошибка возвращают управление, камеру, видимость игрока, звук и состояние персонажей. Reduced Motion и размеры субтитров проверяются в предпросмотре.
- CINE09. Две сцены не могут незаметно одновременно управлять одним NPC/камерой. Конфликт занятости имеет понятное сообщение и авторскую политику ожидания/отмены.

## 13. Предметы и взаимодействия

- ITEM01. Карточка определения: название, описание, модель/иконка, категории, размеры, вес, цена, количество/стек, допустимые действия, квестовые связи и правила сохранения.
- ITEM02. Отдельно редактируются экземпляр в мире и свойства общего определения. Поднять, осмотреть, использовать, перенести, положить, передать по квесту; требования и результаты каждого действия видимы.
- ITEM03. Визуальная настройка применения на цели и комбинации предметов: ингредиенты, количество, условие, расход, результат, звук/анимация и реакция при неуспехе. Списание и выдача атомарны.
- ITEM04. Конструктор взаимодействия использует существующие действия: взять предмет, изменить состояние, показать текст, запустить сцену, подтвердить улику, открыть проход. Для отсутствующего исполняемого действия показывается «требуется новая механика», а не неработающий декоративный блок.
- ITEM05. Предмет, полученный до начала квеста, потерянный, проданный или использованный в другом месте, обрабатывается авторскими правилами. Проверка сообщает о потенциально безвозвратно недоступной обязательной цели.

## 14. Остальной редактируемый контент

Каждый раздел ниже — обязательная часть полной системы. «Форма с произвольным JSON» не считается редактором.

| Раздел | Обязательные возможности и проверяемый результат |
|---|---|
| Документы и записки | Текст, изображения, страницы, автор/дата, локализация, условия доступа, найденные сведения. Созданная записка размещается в мире и открывается в игровом просмотрщике. |
| Улики и расследование | Граф источников, сведений, противоречий и выводов; условия подтверждения; скрытые сведения не раскрываются игроку заранее. Новый вывод появляется только после заданных источников. |
| Журнал | Заголовки, описания целей, порядок/разделы, записи по событиям и состояния прочтения. Предпросмотр пустого, активного и завершённого состояний. |
| Татарский язык | Словарная запись, перевод/варианты, контекст, аудио, примеры, этапы изучения, связь со сценой/документом. Можно создать слово и проверить путь от знакомства до подтверждения. |
| Старый ПК | Документы, папки, сообщения, страницы внутриигрового интернета, ссылки, изображения, даты, доступ и открытия. Предпросмотр в настоящем интерфейсе ПК. Новое произвольное приложение ОС не создаётся автоматически. |
| Магазины | Ассортимент, цены, запасы, расписание, условия покупки и предусмотренный игрой долг/валюта. Это отдельная роль магазина, не общий бартер NPC. |
| Транспорт | Размещение, внешний вид, посадочные места, точки входа/выхода, доступность, существующие параметры движения, звук и квестовые связи. Проверяются безопасная посадка/высадка и сохранение. |
| Головоломки | Сборка из условий, переключателей, последовательностей, предметов, таймеров и состояний объектов; исходы, подсказки, сброс. Произвольная новая физическая симуляция требует отдельной механики. |
| Игровой UI | Визуальная правка существующих меню/HUD/журнала/диалогов: расположение, якоря, размеры, шрифты, цвета, иконки, состояния и привязки к данным. Новые экраны собираются из поддерживаемых компонентов; кнопки связываются с допустимыми действиями. |
| Звук и атмосфера | Музыка, фоновые/локальные звуки, затухание, зоны, условия, субтитры звуков и уровни. Реальное прослушивание обязательно для художественной приёмки. |

UI-конструктор показывает несколько размеров окна и состояний фокуса/ошибки/длинного текста. Перестановка панели не должна ломать клавиатурную навигацию, паузу или сохранение. Переходы экранов задаются явно; изменение UI не даёт скрытого сюжетного прогресса.

## 15. Инструменты для интересного исследования

Ориентир автора «как в Zelda» трактуется как любопытство, пространственные подсказки, несколько подходов и содержательная награда за исследование. Он не означает перенос боевой системы, всего открытого мира или увеличение расстояний ради времени.

- EXP01. Авторские точки интереса с категорией: заметный ориентир, секрет, короткий путь, альтернативный подход, препятствие, находка, сюжетный след. Они могут быть скрыты от игровой карты.
- EXP02. Связи «что привлекает внимание → как добраться → что можно сделать → что изменится/найдётся». Поля служат авторской проверке, а не навязанной игроку цепочке маркеров.
- EXP03. Просмотр линии видимости с высоты игрока, маршрутов и альтернативных проходов; сравнение доступности до/после квеста. Учитываются закрытые двери, высота, коллизии и сюжетные состояния.
- EXP04. Простая запись пути в пробном проходе: пройденный маршрут, остановки, взаимодействия и увиденные автором маркеры. Карта не объявляет автоматически, что игрок заметил секрет или испытал интерес.
- EXP05. Каталог шаблонов окружения: видимый издалека ориентир, скрытый двор, обход, открываемая калитка, новая находка после события. Каждый шаблон полностью редактируется.
- EXP06. Сохранить канон URMAN: зимняя деревня, высокий густой лес без видимого внешнего края, обычный герой и камерное расследование. Редактор не меняет существующий канон молча.

## 16. Пробный запуск и диагностика

- PLAY01. «Играть отсюда» запускает настоящую игру с выбранной точкой появления и ревизией контента в отдельном окне. Возврат открывает тот же объект/шаг в Studio.
- PLAY02. Панель стартового состояния: этапы квестов, выбранные ответы, предметы, знания, время, состояния мира и NPC. Предустановки теста не являются альтернативными версиями контента.
- PLAY03. Различать «достижимый сценарий» и «искусственно заданное состояние». Редактор не выдаёт вручную выставленный финал за обычное прохождение.
- PLAY04. Выбранные условия показывают факт и причину: «нужно 3 доски, есть 2», «NPC занят сценой», «триггер уже сработал», «не найден путь». События имеют время, ID сущности и occurrence ID.
- PLAY05. Пауза, следующий логический шаг, перезапуск контрольной точки, просмотр выбранной ветви. Для сравнения двух исходов достаточно двух изолированных запусков одного контента; отдельные ветки проекта не нужны.
- PLAY06. Время мира и сюжетные таймеры замораживаются при диагностической паузе. Следующий логический шаг — событие/транзакция, а не неопределённое число кадров.
- PLAY07. Debug-запуск использует отдельные saves/preferences/cache. Для URMAN применяется существующая защищённая граница `eng/protected_run.py`; отсутствие защиты блокирует запуск, а не разрешает использовать пользовательские сохранения.
- PLAY08. Выход из игры не применяет игровое состояние к авторским данным. Команда «Взять положение объекта из запуска» доступна только явно с просмотром отличий.
- PLAY09. Редактирование во время игры не меняет незаметно запущенную ревизию. Предлагается остановить/перезапустить сцену с новыми данными; безопасные визуальные обновления могут быть отдельной явно включённой функцией.
- PLAY10. Проверка перед запуском разделяет ошибки схем/ссылок, обнаруженные логические проблемы, геометрию и художественные замечания. Статический анализ не заявляет доказательство достижимости всех ветвей сложной игры.

## 17. Передача контекста разработчику

- HAND01. «Скопировать ID» и «Скопировать контекст» доступны у каждой сущности и черновика. Вставка ID в поиск возвращает объект и нужный подраздел.
- HAND02. Контекст содержит проект, ревизию, ID/имя/тип, цепочку до родительского квеста, связанные объекты, активное состояние, выделенное поле/шаг, авторское описание проблемы и компактные диагностические сообщения.
- HAND03. Для сбоя создаётся отдельный case ID. Пакет включает начальное состояние проверки, действия/события до сбоя, ожидаемый и фактический результат, версии формата/игры, отпечатки контента, камеру и при необходимости кадр. Ограничения воспроизведения внешних/физических событий указываются честно.
- HAND04. Для только что созданного квеста передаётся сам черновик с зависимостями либо компактное изменение относительно известной ревизии. Одного ID нет в другой копии проекта — редактор предупреждает об этом, а не копирует бесполезную ссылку.
- HAND05. Два формата: читаемый текст для вставки в чат и переносимый пакет с манифестом. Автор видит состав/размер, может исключить тяжёлые медиа; исходные пути пользователя и несвязанные saves не включаются по умолчанию.
- HAND06. Предложение изменений от разработчика содержит базовую ревизию, затронутые ID/поля, описание и данные. Studio показывает разницу, проверяет устаревшую базу и применяет выбранное только после действия автора. Нет встроенного ИИ, автоматической отправки в чат или исполнения присланного кода.
- HAND07. Защищённый автором объект/поле помечается при любом входящем изменении. Защита не скрывает конфликт и не даёт молча заменить результат ручной работы генерацией.

Пример пользовательского сообщения, создаваемого кнопкой:

> Квест «Доски для Тамары», ID …, черновик, ревизия … . Шаг «Вернуться», ID … . После передачи 6 досок калитка осталась закрыта. Ожидается состояние «починена». Case ID … . Приложены черновик, связанные объекты и начальное состояние запуска.

## 18. Сохранение, восстановление и совместная работа

### 18.1. Локальная надёжность

- SAVE01. Отмена/повтор охватывает текст, поля, трансформации, связи, удаление, кисти, геометрию и таймлайн. Перетаскивание/штрих — одна команда; составное действие отменяется целиком.
- SAVE02. Автосохранение черновиков не реже чем каждые 30 секунд после завершённого действия; Cmd+S сразу сохраняет. После сбоя потеря не превышает интервал автосохранения, если диск был доступен.
- SAVE03. Запись атомарная; при нехватке места/прав сохраняются последняя целая версия и текущие несохранённые данные в памяти. Ошибка остаётся видимой; «сохранено» не показывается раньше подтверждения.
- SAVE04. Именованные контрольные версии с описанием, временем и автором; можно посмотреть изменения и восстановить выбранную версию как новую ревизию. История не превращается в интерфейс альтернативных карт.
- SAVE05. Отмена собственных действий после получения чужих изменений не откатывает чужую работу. Если обратная операция конфликтует, показан тот же интерфейс разрешения конфликта.
- SAVE06. При старте после сбоя показаны восстановленный черновик, последняя ручная версия и отличия. Пользователь не обязан искать временные файлы.

### 18.2. Совместное редактирование

Предлагаемая модель первой полной поставки: несколько участников одновременно работают в своих локальных редакторах, получают и отправляют ревизии через настроенный общий источник; объединение выполняется по сущностям и полям. Живые курсоры и мгновенное синхронное перетаскивание одного объекта, как в Figma, не включены без отдельного решения. Это не ограничивает одновременное редактирование разных частей проекта.

- COLLAB01. У каждого изменения есть base revision, автор, затронутые ID/поля и результат. У автора есть «Получить изменения», «Посмотреть», «Объединить», «Отправить»; команды Git/ручные маркеры конфликта не требуются.
- COLLAB02. Изменения разных сущностей или независимых полей объединяются автоматически, если итог проходит семантическую проверку. Даже изменение разных объектов может конфликтовать через общую ссылку/квест — это проверяется после объединения.
- COLLAB03. Одно поле изменено по-разному: база / моё / входящее с понятными названиями. Трансформации показаны в 3D, диалог — репликами, граф — блоками и стрелками. Варианты: оставить одно, вручную собрать итог, отложить.
- COLLAB04. Удаление против редактирования/новой ссылки всегда явный конфликт. ID удалённого объекта не выдаётся другому; информация об удалении сохраняется для объединения.
- COLLAB05. Упорядоченные списки объединяются по ID элементов, а не индексам массива. Несовместимый порядок или взаимные зависимости показываются пользователю; строки файлов не служат моделью объединения.
- COLLAB06. Бинарные модели, текстуры и аудио не объединяются как текст. Автор выбирает ресурс, сохраняет второй как отдельный новый ресурс с переназначением либо откладывает. Для тяжёлого редактирования модели доступна отметка занятости; работа офлайн не делает её безусловной гарантией.
- COLLAB07. Внешняя правка файла разработчиком обнаруживается. Если есть локальная правка того же объекта, данные не перезагружаются поверх неё; открывается сравнение.
- COLLAB08. При отключении сети локальная работа/сохранение продолжаются. Отправка повторяется явно; неизвестный результат передачи проверяется по ID операции, а не создаёт дубликат.
- COLLAB09. Не использовать одну общую папку как бесконтрольное одновременное хранилище нескольких писателей. Второй процесс на той же локальной рабочей копии открывается только для чтения либо согласованно передаёт владение.
- COLLAB10. Получение/отправка не публикуют билд и не включают несвязанные изменения исходников. Общий транспорт предлагается строить поверх существующего репозитория/ревизий; новый облачный сервис и аккаунты не являются скрытой зависимостью редактора. Конкретный транспорт фиксируется до реализации этого этапа.

## 19. Архитектура и технические инварианты

### 19.1. Рассмотренные варианты

| Вариант | Оценка |
|---|---|
| Плагин обычного редактора Godot | Максимум готовых редакторских инструментов, но пользователь остаётся в среде движка. Не выбран как основной пользовательский интерфейс из-за U01/U02; отдельные средства разработчика допустимы. |
| Отдельное приложение на Godot/.NET с общими библиотеками URMAN | Рекомендуемый вариант: собственный интерфейс, общие представление и игровое исполнение. Не означает, что инструменты моделирования/квестов уже существуют в движке. |
| Браузерный редактор + отдельная 3D-игра | Не выбран: противоречит выбранному формату и добавляет второй слой представления/интеграции для проверки мира. |

Рекомендация является проектом технического решения. Не создавать второй игровой runtime или копию квестового редьюсера ради быстрого прототипа.

### 19.2. Владельцы

- Studio владеет пользовательскими командами редактирования, черновиками, представлениями, историей и диагностическим интерфейсом.
- `Urman.Content` остаётся владельцем форматов, компиляции и ссылочной целостности; Studio использует его напрямую, CLI сохраняет свою роль.
- `Urman.Core` остаётся владельцем игровых фактов/транзакций/жизненного цикла квестов.
- Godot-слой игры остаётся владельцем физики, камер, анимаций, звука и реализации игровых действий.
- Авторские ресурсы мира хранят постоянные ID, иерархию, трансформации и параметры; ресурсы движка с геометрией/материалами не попадают в portable narrative kernel.
- Скомпилированные пакеты, превью, навигационные производные и кеши воспроизводимы и не являются первоисточником. Нужные исходники модели, аудио и авторские изменения не считаются кешем.

### 19.3. Правила исполнения и хранения

1. Один экземпляр сущности и один владелец каждого вида состояния. При переносе участка из генератора в авторские данные старый путь перестаёт управлять этим участком; постоянный fallback с двумя владельцами запрещён.
2. UI редактирования использует типизированные операции. Мутация DOM/контролов/видимых Godot-узлов без записи авторской модели не считается сохранённым изменением.
3. Логика квестов отделена от пространственного исполнения, но связана устойчивыми ID. Привязка к имени узла сцены или номеру строки запрещена.
4. Читаемые версионированные источники; детерминированная сериализация; минимальные изменения файлов. Монолит, переписывающий все квесты при одной реплике, не допускается. Конкретное разбиение существующих модулей определяется совместимостью компилятора.
5. Валидация черновика не требует его готовности к игре; компиляция выбранной кампании проверяет ссылки и доступность нужных действий.
6. Каждая runtime-ревизия имеет отпечаток. Совместимость сохранений определяется явными правилами миграции и ID; текущую проверку fingerprint нельзя просто отключить.
7. Незнакомая новая версия схемы не перезаписывается старым редактором; доступен просмотр/сообщение об обновлении. Миграция данных сохраняет возможность восстановления.
8. Импорт и внешние пакеты не выполняют содержащийся в них произвольный код. Проверяются пути, типы, размеры и ссылки; повреждённый ресурс не портит существующий проект.
9. Сборка, импорт и захват сериализуются в пределах проекта. Studio показывает занятую операцию и не запускает конкурирующий импорт во время записи того же ресурса.

### 19.4. Повторное использование средств платформы

Для истории обратимых команд рассмотреть штатный [UndoRedo Godot 4.7](https://docs.godotengine.org/en/4.7/classes/class_undoredo.html). Для отображения графа — [GraphEdit](https://docs.godotengine.org/en/4.7/classes/class_graphedit.html): он предоставляет визуальные элементы и события взаимодействия, но модель квеста, проверка связей и исполнение остаются ответственностью URMAN. [EditorPlugin](https://docs.godotengine.org/en/4.7/classes/class_editorplugin.html) относится к расширению редактора движка, поэтому не следует считать его автоматически доступным механизмом отдельного экспортируемого Studio. Источники проверены 27 сентября 2026; конкретные API сверяются с версией проекта при реализации.

## 20. Перенос существующей игры

1. Снять актуальный срез текущих источников и доступных данных; прочитать чужие изменения. Переносить работающий результат, не старую историческую сборку.
2. Составить реестр сущностей существующей деревни/квестов: ID, владелец, источник, способ редактирования и ограничения. В Studio показать покрытие «редактируется / требуется перенос»; не скрывать неподдержанный контент.
3. Сначала открыть существующие повествовательные данные без потери неизвестных полей; проверить цикл открыть → сохранить без изменений: содержательных изменений быть не должно.
4. Для выбранного законченного участка извлечь параметры из C# в авторские данные, сохранив ID и поведение. После успешного перехода отключить старого владельца только этого участка, без параллельной полной переделки мира.
5. Провести через редактор существующий квест Тамары: расстановка, камеры, маршрут, реплики, предметы, итоговое состояние, пропуск и загрузка. До переноса сравнить обычный сценарий; после — убедиться, что редактируются реальные production-данные.
6. Расширять покрытие деревни и контента пакетами с явным перечнем. Полная приёмка Studio требует редактируемости всего обещанного состава U01–U18, а не только демонстрационного квартала.
7. Миграция сохранений — отдельный контракт. Если конкретное изменение несовместимо, объяснить причину и предложить изолированный новый тестовый запуск, не удаляя пользовательские saves.

## 21. Нефункциональные требования и хранение файлов

Предлагаемые целевые показатели ниже проверяются на зафиксированном Mac автора с указанными моделью, памятью, macOS, размером viewport и настройками. Сейчас измерения не выполнялись; точная машина остаётся параметром приёмки.

| Область | Целевой критерий |
|---|---|
| Простые действия UI | Видимая реакция на выбор/поле/кнопку ≤100 мс в 95% измерений, тяжёлая операция показывает начало и прогресс, допускает отмену. |
| Поиск | Результат ≤300 мс для каталога 1 000 записей и кампании 100 квестов после индексации. |
| Граф | Кампания до 100 квестов; внутренний квест до 200 одновременно видимых блоков. Перемещение/масштаб без длительных зависаний; свёртка и фильтры для больших графов. |
| Мир | Текущая деревня и ещё 25% размещённых экземпляров: не менее 30 FPS при согласованных настройках viewport; во время редактирования качество можно снизить с явной индикацией. Художественный предпросмотр использует игровые настройки. |
| Запуск проверки | Цель ≤15 секунд для тёплого запуска существующего участка после правки текста/трансформации без переимпорта тяжёлых ассетов. Холодный импорт измеряется отдельно. |
| Сохранение | Простая правка не требует полной пересборки мира. Автосохранение ≤30 секунд; ошибка диска не уничтожает предыдущую целую версию. |
| Длительная работа | Четырёхчасовой авторский сеанс с многократными запусками/закрытиями и импортом не накапливает незакрытые процессы и неограниченный кеш. |

Файловая дисциплина:

- Все временные запуски, превью и захваты имеют собственный каталог и манифест владельца с ID запуска. Удаляются только перечисленные производные файлы, а не произвольное содержимое `/tmp`, проекта или загрузок.
- Предлагаемые значения: общий лимит автоматически удаляемого кеша 2 ГБ; до 10 последних незакреплённых отчётов. Перед генерацией большого видео показывается оценка места; непрерывная запись по умолчанию выключена.
- Исходники, именованные версии, закреплённые отчёты и пользовательские сохранения не удаляются по возрасту. Если они занимают много места, показывается разбивка и явное действие автора.
- Отмена импорта/проверки удаляет только собственные незавершённые производные файлы. Очистка и её объём видны в настройках.
- Работа над контентом возможна офлайн; сеть нужна только для явно настроенного обмена. Установленные компоненты и недоступные функции показываются до начала соответствующего сценария.

## 22. Порядок реализации и границы поставок

Все этапы обязательны для полного ТЗ. Порядок не означает отказ от поздних модулей. Календарные сроки не назначаются до проверки трёх рисков: перенос текущего мира из кода, встроенное моделирование и семантическое объединение изменений.

| Этап | Пользовательский результат | Условие выхода |
|---|---|---|
| P0. Интерфейс и технические границы | Автор проходит прототип без объяснения внутренних терминов; выбран реальный путь хранения/моделирования/обмена. | Пять экранов §4.2 просмотрены автором; технические эксперименты ограничены своими задачами, не объявлены готовым продуктом. |
| P1. Один сквозной рабочий участок | Можно изменить кусок существующей деревни, создать связанный квест/диалог/предмет/триггер и пройти два исхода. Есть ID, отмена, сохранение, изолированный запуск. | Сквозной сценарий работает на настоящем runtime; карта и квесты поставляются вместе. |
| P2. Вся деревня и каталог | Расстановка, интерьеры, рельеф, дороги, растительность, материалы, свет, звук, сюжетные изменения мира. | Обещанные объекты текущей деревни доступны для редактирования; перезапуск сохраняет ручные изменения. |
| P3. Полная логика и постановка | Все отношения квестов, сложные диалоги, расписания NPC, библиотека анимаций, камеры и монтажная шкала. | Тамара полностью проходит из редакторских данных; обычный сценарий, пропуск, сохранение/загрузка дают согласованный результат. |
| P4. Остальные игровые редакторы | Все разделы §14 и предметные взаимодействия редактируются без JSON. | Для каждого раздела выполнен указанный игровой сценарий. |
| P5. Геометрия и персонажи | Встроенное создание/редактирование моделей, лица, одежды и нового персонажа. | Пять сценариев MODEL07 пройдены в Studio с игровым предпросмотром. |
| P6. Объединение и окончательная приёмка | Несколько участников вносят и совмещают изменения; восстановление, передача контекста и удобство подтверждены. | Матрица §23 пройдена; оставшиеся ограничения перечислены, пользовательская приёмка проведена. |

Стабильные ID, ревизии, типизированные операции, сохранение и отсутствие потери чужих правок проектируются с P1. P6 завершает пользовательский интерфейс и сценарии совместной работы, а не вводит задним числом новую несовместимую модель данных.

Перед каждым пакетом реализации: назвать пользовательский эффект и проверяемый результат. После: проверить затронутый сценарий, обновить единственный существующий трекер, отделить технический результат от человеческой оценки. Новый объём фиксировать изменением ТЗ, а не прятать внутри пакета.

## 23. Приёмка

Это сценарии будущей проверки, не результаты выполненных тестов. Автоматизация должна быть соразмерна изменению; полный запуск всех проверок на каждую правку интерфейса не требуется. Защищённые игровые запуски обязательны.

| ID | Сценарий | Готово, когда |
|---|---|---|
| A01 | Новый пользователь | Автор без опыта после встроенного знакомства находит каталог, ставит объект, отменяет, сохраняет и запускает игру без терминала. |
| A02 | Дом как целое | Перемещены дом, интерьер, входы и связанные точки; в игре можно войти/выйти, дверь и коллизии находятся там же, где геометрия. |

| A04 | Основные/побочные квесты | Все три представления кампании показывают одни сущности; сортировка не меняет доступность, явная зависимость — меняет. |
| A05 | Список ↔ граф | Развилка, параллельная группа и объединение переживают редактирование в обоих видах, сохранение и загрузку без потери логики. |
| A06 | Карта ↔ квест | Из триггера открыт шаг; из шага найдена область; созданная связь исполняется в игре и отменяется одной командой. |
| A07 | Два исхода | Игрок принимает/отклоняет условие, получает разные реплики и последствия; выполнение/провал правильно открывают последующие задания. |
| A08 | Мир после квеста | Калитка/завал меняют видимость, физику и путь; персонаж не оказывается внутри появившегося объекта. |
| A09 | Повторный триггер | Повторный вход/событие и загрузка не дублируют награду; повторяемый квест следует явно заданной политике. |

| A19 | Два участника | Разные объекты/поля объединяются; одно поле, удаление против правки, порядок шагов и бинарный ресурс показывают понятные конфликты. |
| A20 | Восстановление | После сбоя/отказа записи открывается целая версия и доступный черновик; чужие изменения не теряются при Undo. |
| A21 | Моделирование | Все пять MODEL07 выполнены внутри Studio; результат появляется в каталоге и настоящей игре. |

| A23 | Исследование | На изменённой улице есть заметный ориентир, скрытая находка, два подхода и открываемый короткий путь; человек описывает, что заметил и зачем исследовал. Количество объектов не заменяет оценку. |

Продукт нельзя объявлять полностью готовым, пока A21/A22/совместная работа существуют только в планах. Возможна честно обозначенная промежуточная поставка P1–P3 с перечнем ещё отсутствующих модулей.

## 24. Решения для следующего согласования

Продуктовые ответы U01–U18 зафиксированы. До основной реализации остаются следующие конкретные решения:

1. Визуальный прототип: автор оценивает пять экранов §4.2. Опыт работы с профессиональным редактором не предполагается.
2. Совместная работа: подтвердить достаточность параллельной работы с получением/объединением ревизий. Если нужно видеть чужие движения немедленно в том же мире, это отдельное расширение сетевого контракта и оценки.
3. Точная модель Mac/память/версия ОС и рабочий размер окна — для численной приёмки, определяются чтением окружения перед реализацией, а не догадкой.
4. Технический выбор встроенного моделирования и транспорта совместной работы — задача разработчика с ограниченным исследованием. Если доступные средства требуют заметного изменения UX, лицензии или установки внешнего приложения, решение возвращается автору до реализации.

Предложенные значения производительности, интервалов/лимитов, первая библиотека анимаций и трактовка квестовой передачи предметов являются частью проекта ТЗ, а не цитатами автора. Их можно корректировать явно. Полный объём не уменьшать молча ради первого прототипа.
