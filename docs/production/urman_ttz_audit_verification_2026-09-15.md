## 1. Метод и что удалось прогнать

Что делалось:

- повторное чтение кода по каждому реперному пункту (не по названиям файлов, а по
  фактическому пути исполнения: кто вызывает, при каких условиях, что происходит дальше);
- поиск по всем терминам §27–28 ТЗ, включая Godot-эквиваленты Unity-конструкций
  (`Area3D`, `body_entered`, `get_overlapping_bodies`, `intersect_shape`, `Knock`,
  `DoorKnock`, `HouseInteraction`, `proximity`);
- декодирование InputMap из `game/project.godot` (клавиши и кнопки геймпада по индексам);
- история git по удалённым/существовавшим механикам (`-S` по строкам);
- **прогон JS-тестов**, которые в этой среде выполнимы:
  `npm run content:check`, `npm run test:content`, `npm run test:runtime`;
- анализ собранного пака `game/content/urman.chapter1.compiled.v1.json` (что реально
  попадает в билд);
- поиск покрытия тестами каждого спорного утверждения.

Что прогнать **нельзя** в этой среде (и это честная граница доказательств):

- Godot-смоуки (`game/tests/*.cs`): в репозитории нет `.tools/godot/...` (Godot не
  установлен), а `eng/run-smoke-guarded.sh` требует ещё и внешний `protected_run.py`
  по пути другой машины;
- .NET-сборка и компилятор контента: `dotnet` в среде отсутствует (`.tools/dotnet` нет).
  Поэтому утверждения о поведении внутри движка проверены **статически по коду** и
  отмечены как таковые; всё, что подтверждено прогоном, помечено «прогнано».

## 3. Новые находки (в первом аудите отсутствовали)

### N1. Фотография Марата на въезде недостижима в игре (дефект прогрессии)

**Факт.** `ArrivalPhotoTarget` создаётся с **пустым** `interactionId`:

```
game/scripts/Act1ConnectedWorld.ExteriorDiscoveries.cs:77–83
village.MakeInteractionBox("ArrivalPhotoTarget", new(.60f,.60f,.50f), …,
    "665b49", "",                       // ← interactionId пуст
    "Посмотреть фотографию",
    documentId: "urman.chapter1:document/arrival-photo-evidence", rayOnly: true);
```

**Путь исполнения (почему цель мертва):**

- `InteractionTarget._Ready` → `RefreshAvailability()` (`InteractionTarget.cs:164–187`)
  спрашивает `_bridge.IsInteractionAvailable("")`;
- `RuntimeBridge.IsInteractionAvailable` (`RuntimeBridge.cs:389–405`) первым делом
  делает `_content.TryGetInteraction(interactionId, …)` → `CompiledCampaignRepository.cs:214–215`
  (словарь `_interactionsById`) → для `""` промах → `false`;
- значит `_available=false`, `CollisionLayer=0` (`InteractionTarget.cs:179`), и
  `Interact()` делает ранний выход (`InteractionTarget.cs:70–74`);
- `Act1ConnectedWorld.ApplyInteractionRouting` (`Act1ConnectedWorld.cs:606–630`) на
  каждом изменении состояния **повторно** гасит слой, потому что условие
  `binding.Node.IsAvailable()` ложно навсегда (`:619`).

**Проверка по собранному паку** (`game/content/urman.chapter1.compiled.v1.json`):
документ в паке есть (`registries/documents[0]`), его `openEffects` подтверждают
`memory_marat_childhood_photo`, `memory_marat_kazansky_ne_otstavay` и запись в журнал,
но **ни одна сущность пака не ссылается на этот документ** (скан по `documentId` —
0 совпадений). То есть в игре нет ни одного пути к нему.

**Почему это важно.** Коммит `dae801d` («make the arrival memory of Marat a player
action (M1)») убрал автоматическую выдачу этих двух фактов из `onEnter` сцены приезда
и перенёс их в документ, который должен был открываться с этой цели. В итоге память
Марата в билде **не получить**: карточки в журнале нет, два факта скрыты. Квесты от них
не зависят (проверено: в контенте нет условий на `memory_marat_*`), поэтому софт-лока
нет — но заявленная механика M1 в текущем коде не работает.

**Покрытие тестами.** Физическую цель не проверяет ни один тест: `JournalFlowSmokeTest.cs:159`
открывает документ программно (`bridge.OpenDocumentAsync(...)`), а обходной тест фото не
касается (grep `photo` по `Act1FirstPersonWalkthroughSmokeTest.cs` — 0). Это объясняет,
почему дефект не был пойман.

**Что сделать.** Дать цели реальный id (например, добавить в контент
`interaction/arrival-photo` с `targetDocumentId`) и тест, который подходит к скамейке и
берёт фото физическим лучом.

> Статический вывод из кода детерминирован; для окончательного «в билде не работает»
> нужен прогон Godot-смоука, который в этой среде недоступен (см. §1).

### N3. Валидация контента сейчас красная: 9 падающих тестов, одна причина

Прогнано в этой среде:

| Команда | Результат |
| --- | --- |
| `npm run content:check` | **FAIL** — пачка `UndeclaredDependency` |
| `npm run test:content` | 62 pass / **6 fail** из 68 |
| `npm run test:runtime` | 99 pass / **3 fail** из 102 |

Единственная причина у всех девяти падений: модуль `urman.chapter1` ссылается на
документы `urman.oldpc` в `journalAction.sourceIds`
(`content/modules/urman-chapter1/definitions.json`, указатель `/169/interactions/*/journalAction/sourceIds/*`),
а его манифест объявляет `"dependencies": []` (`content/modules/urman-chapter1/module.json:25`).
Валидатор: `scripts/content/compile-content.mjs:496` и `:728`.

Дополнительно:

- направление зависимостей уже обратное: `urman.oldpc` зависит от `urman.chapter1`
  (`content/modules/urman-oldpc/module.json:51–56`), поэтому просто «объявить
  зависимость» нельзя — это создаст цикл, а циклы фатальны (тест «module dependency
  cycles are fatal»);
- тест-контракт прямо требует, чтобы chapter 1 **не** упоминал oldpc
  (`tests/content/urman-chapter1/chapter1-data.test.mjs:59–64`: `dependencies` пуст и
  манифест не содержит `urman.oldpc:`);
- в поставляемом паке эти ссылки **есть**: скан `game/content/urman.chapter1.compiled.v1.json`
  даёт 9 `journalAction`, и все 9 ссылаются на `urman.oldpc:document/*` — то есть
  .NET-компилятор кампании это пропускает (модули перечислены в кампании), а
  JS-аудит модуля — нет;
- ссылки введены коммитом `401f5bd` («Make Act I deductions depend on player comparisons»);
- `content:check` не гейтится ни одним скриптом `eng/*`, поэтому расхождение
  накопилось незамеченным, хотя `content_authoring_guide.md:243` требует его зелёным.

**Что сделать (решение уровня архитектуры, не правка одной строки).** Либо вынести
9 сравнений из `scene/investigation-journal` в модуль, которому разрешено зависеть от
обоих (например, новый `urman.investigation`, который включается в кампанию после
`urman.oldpc`), либо принять обратное направление и пересобрать граф так, чтобы
`urman.oldpc` не зависел от `urman.chapter1`. После — добавить `content:check` в
gate-скрипт, чтобы расхождение не повторялось.

### N4. `section` у старого ПК реализован в capability, но не вызывается из UI

`OldPcCapabilityProvider.Handle` поддерживает `search/open/save/**section**`
(`src-dotnet/Urman.Core/Capabilities/OldPc/OldPcCapabilityProvider.cs:111–149`), а
`RuntimeBridge.HandleOldPcInputAsync` его пропускает (`RuntimeBridge.cs:678–681`).
Единственное вхождение строки `"section"` во всём `game/` — эта самая ветка: UI
(`OldPcUi.cs`) всегда отправляет только `search`/`open`/`save`, тестов на `section`
нет (grep по `game/tests`). То есть **навигации по разделам в билде нет**, хотя
модель данных её предусматривает: разделы видны игроку только внутри пути
`C:\KYRLAY\<раздел>\<id>.txt` в строке статуса (`OldPcUi.cs:151`).

### N5. Подсказка геймпада для взаимодействия расходится с текстом интро

`interact` привязан к двум кнопкам геймпада — `button_index=1` (B/Circle) и `0` (A/Cross),
клавиатура — `E`. Подсказка берёт **первую** найденную кнопку (`FirstPersonController.RefreshInteractionHints`,
`FirstPersonController.cs:551–586`), а порядок событий в проекте — B, A, поэтому в игре
игрок увидит `[B]`, тогда как интро-панель говорит «A — начать / осмотреть»
(`Act1DemoRoot.cs:1127–1129`). Косметика, но при отладке геймпада путает.
